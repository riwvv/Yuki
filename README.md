# Yuki

Личный ИИ-компаньон, а не голосовая команда «включи свет». Yuki — переосмысление и духовный преемник моего предыдущего проекта, [Jarvis](https://github.com/riwvv/Jarvis), после того как я упёрся в его архитектурный потолок.

> Статус: активная разработка. Голосовой диалог с Host, Resource Manager и Servant с поддержкой Tool Calling работают вживую.

## Зачем ещё один личный ассистент
Jarvis строился на одной LLM, которая отвечала и за разговор, и за выполнение задач — в итоге получалась не столько компаньон, сколько привычная схема умных колонок: «получил команду → выполнил → ответил». Плюс жёсткая зависимость от отдельно установленной Ollama и рваная нагрузка на железо (то простой, то полная загрузка при любом обращении).

Yuki строится вокруг четырёх целей:
- **Скорость** — живой разговор, а не ожидание ответа.
- **Мульти-агентность** — разделение на Host и Servant вместо одной модели на всё.
- **Эффективное использование железа** — осознанное распределение по CPU/GPU, никакого простоя-впустую.
- **Независимость от внешних сервисов** — всё локально, без обязательных сторонних рантаймов.

## Что уже работает

- **Голосовой диалог** — кастомно обученная wake-word модель → детекция речи (VAD) → потоковое распознавание (Vosk) → ответ Host в характере, воспроизводимый через модуль TTS, без ожидания полного ввода.
- **Servant с Tool Calling** — фоновый агент-исполнитель, который принимает задачу от Host, планирует последовательность вызовов инструментов (плагинов) и возвращает результат. Реализован полный цикл: модель генерирует JSON-вызов → коннектор `YukiChatCompletion` преобразует его в `FunctionCallContent` для Semantic Kernel → функция выполняется через `Kernel` → результат возвращается модели для формирования финального ответа. Поддерживаются многошаговые сценарии (несколько инструментов подряд в рамках одной задачи).
- **Структурированный вывод через GBNF** — три грамматики (`tool_calling.gbnf`, `user_interaction.gbnf`, `dialog_only.gbnf`) гарантируют, что модель генерирует только валидный JSON заданной структуры. Это устраняет необходимость эвристического парсинга «сырого» текста и делает поведение предсказуемым.
- **Resource Manager** — живой мониторинг свободной VRAM и безопасная «горячая» перезагрузка Host'а на лету при изменении внешней нагрузки на GPU (например, запуск игры во время разговора): число GPU-слоёв пересчитывается и подстраивается сама по себе, без потери контекста и без остановки диалога — Юки сама замечает изменение обстановки и предупреждает об этом, а не молча тормозит или падает.

## Архитектура (коротко)
- **Host** — разговорное лицо Yuki. Решает, отвечать самой или делегировать задачу Servant'у, ведёт диалог в характере. Использует GBNF-грамматику `user_interaction.gbnf` для строгого формата ответа (текст + опциональный tool call) и `dialog_only.gbnf` для чисто диалоговых системных событий. История диалога автоматически очищается при достижении лимита сообщений с пересозданием инференс-движка для сброса KV-cache.
- **Servant** — специалист по выполнению задач и tool calling, с инвентарём плагинов. Для изоляции контекста между задачами используется `StatelessExecutor`: каждая задача обрабатывается с чистого состояния, что исключает накопление «мусора» в KV-cache от предыдущих вызовов. Кастомный коннектор `YukiChatCompletion` реализует `IChatCompletionService` Semantic Kernel и берёт на себя цикл автоматического вызова инструментов, валидацию tool call (существование функции, наличие обязательных аргументов) и обработку ошибочных ответов модели.
- Обе роли — независимо настроенные экземпляры одной и той же LLM-инфраструктуры (llama.cpp), не разные модели ради разных задач.
- **Resource manager** отвечает за то, какая модель когда загружена и сколько слоёв уходит на GPU — обе живут ровно столько, сколько реально работают, не дольше.

## Ключевые технические решения
- **GBNF-грамматики** — принудительная генерация JSON заданной структуры на уровне сэмплера, а не пост-фактум парсинг. Грамматика `user_interaction.gbnf` ограничивает `args` строго полем `"task"`, исключая попадание посторонних ключей.
- **Stateless-инференс для Servant** — каждая задача начинается с чистого KV-cache, что критично для стабильности многошагового Tool Calling на моделях малого размера.
- **Валидация tool call в коннекторе** — до вызова `InvokeAsync` проверяется существование функции в `Kernel` и наличие всех обязательных параметров. При ошибке модель получает структурированное сообщение и может исправиться без прерывания цикла.
- **Nudge-логика** — при пустом ответе модели коннектор добавляет в историю явную инструкцию и повторяет генерацию ограниченное число раз, после чего возвращает осмысленный fallback вместо пустой строки.
- **Параметры сэмплинга** — для Qwen3.5-4B подобраны `RepeatPenalty`, `PresencePenalty` и `FrequencyPenalty`, предотвращающие зацикливание на повторении фраз в длинном контексте.

## Стек
- **.NET / WPF** — основное приложение.
- [**LLamaSharp**](https://github.com/SciSharp/LLamaSharp) (llama.cpp) — локальный инференс LLM.
- **Microsoft Semantic Kernel** — оркестрация плагинов и Tool Calling; кастомный коннектор `YukiChatCompletion` связывает Semantic Kernel с LlamaSharp.
- **Vosk** — потоковое распознавание речи (STT), приоритет — минимальная задержка отклика.
- **ONNX Runtime** — детекция ключевого слова (кастомно обученная модель, без сторонних SDK/аккаунтов).
- **LibreHardwareMonitorLib** — живой мониторинг VRAM для Resource Manager'а.
- **Supertonic 3 (ONNX)** — локальный синтез речи (TTS), работающий полностью в оффлайне.
